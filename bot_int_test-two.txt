## 1. L'objectif de ma question

Le scénario :

> « Remboursement ≤ 50 € → autonome ; remboursement > 50 € → validation humaine »

ne cherchait **pas** à te faire programmer exactement cette règle.

Je cherchais à tester si ton agent comprend le concept d'**autonomie conditionnelle**.

Un véritable agent métier ne devrait pas fonctionner uniquement comme :

```text
AUTORISÉ
    ↓
ACTION

INTERDIT
    ↓
REFUS
```

Il devrait pouvoir avoir des **politiques d'action** :

```text
Demande
   ↓
Identifier l'action
   ↓
Évaluer le risque
   ↓
Vérifier les permissions
   ↓
Vérifier les conditions
   ↓
┌───────────────┬────────────────┬─────────────────┐
│ Automatique   │ Validation     │ Interdiction   │
│               │ humaine        │                 │
└───────────────┴────────────────┴─────────────────┘
```

### Exemple

Une entreprise pourrait définir :

| Action                        | Politique   |
| ----------------------------- | ----------- |
| Répondre à une FAQ            | Automatique |
| Recommander un produit        | Automatique |
| Créer un ticket               | Automatique |
| Modifier une commande         | Validation  |
| Remboursement ≤ 50 €          | Automatique |
| Remboursement > 50 €          | Validation  |
| Modifier le prix d'un produit | Interdit    |
| Supprimer un produit          | Interdit    |

**C'est cette architecture que je voulais tester.**

# 2. Est-ce que tu devrais programmer cette logique ?

### Oui, absolument — mais pas en dur dans le prompt.

C'est un point très important pour ton projet.

Tu ne devrais pas avoir :

```text
"Si remboursement inférieur à 50 €, rembourse."
```

dans le prompt de l'agent.

Il vaut mieux avoir un **Policy / Permission Engine** indépendant du LLM.

Par exemple conceptuellement :

```json
{
  "action": "refund",
  "mode": "conditional",
  "conditions": {
    "amount_max": 50,
    "currency": "EUR"
  },
  "approval_required_above": 50
}
```

Puis ton agent demande au moteur :

```text
Can I execute "refund" for 35 EUR?
```

Le moteur répond :

```text
ALLOWED
```

Pour 150 € :

```text
HUMAN_APPROVAL_REQUIRED
```

Et pour une action interdite :

```text
DENIED
```

### C'est beaucoup plus sécurisé.

Le LLM **propose une action**.

Le moteur de permissions **décide si elle est autorisée**.

Le système d'exécution **effectue réellement l'action**.

> **Ne modifie pas encore ton architecture pour reproduire ce comportement.**

Il faut d'abord comprendre ce qui s'est passé.

Il y a plusieurs possibilités :

### A. Limite de contexte / quota

Le backend pourrait avoir atteint une limite et basculer sur une réponse de fallback.

### B. Erreur de récupération de conversation

Ton frontend affiche seulement le dernier échange parce que le chargement de l'historique a échoué.

### C. Reset du thread

Ton backend pourrait avoir créé une nouvelle session/conversation.

### D. Limitation volontaire de sécurité

Une règle pourrait déclencher :

```text
risk / token / usage / timeout
       ↓
fallback
```

### E. Timeout backend

Le LLM ou un service intermédiaire pourrait avoir dépassé un timeout et ton système retourne un message générique.

### F. Problème de persistance

Le message courant est enregistré, mais la récupération des anciens messages échoue.
